## Description

Post-condition contracts are essentially checking the return result of a function and 'totally freaking out' if the return result breaks the contract. In other words, the contract expression returned false.

Attached is a patch that allows for post condition checks: that is, decorating a method with [required] will allow you to perform a check against the expression about to be returned by the function.

In the case of doing a post-condition check, you'll want to use "result" to represent the value about to be returned from the function – it will be resolved to the returning type.

[required(result != "")]

def condition([required]input as string):

 return input

condition("Dance party ! ! !")

(wanna see something neat? Fire up Boo Explorer for Windows after you've applied the patch, copy the above code, and press period after 'result' to see Boo actually do accurate code completion depending on what type condition() returns!)

Overloading the [required] attribute made perfect sense in my opinion.

The main functionality - checking for errors - would be exactly the same if I created a new attribute for it, and so would the syntax be.

Overloading [required] was meant to keep the syntax simple and familiar, and not duplicate code (any new attribute would have had to use the same error checking used in [required] anyway). Required parameters, required result, etc.

Doug,

I considered putting the attribute there, but figured it would look horifyingly ugly. Plus it would kind've shorten up how much space you have for the expression to validate the result of the method.

Assuming [required()] properly handles pre- and post-conditions, what else needs to be done to enable more robust Design By Contract code?

### Doug H, 20/Jul/05 10:50 AM

"ensure" is a keyword already in boo, so it wouldn't work as an attribute name.

Attributes can be placed on the return type of a method, too, like below, but I'm not sure that it looks any better.

def condition([required]input as string) [required(result != "")]:

 return input

The attribute will be attached to the method's ReturnTypeAttributes property.

Eventually we can work on implementing full DBC and AOP support to boo perhaps, with pre,post,invariant,before,after,around macros and attributes. But you have to check inheritance, too. For example a subclass can only weaken the precondition and strengthen the postcondition. See Eiffel.
