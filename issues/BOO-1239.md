# BOO-1239: Regex Literals should not take precedence over a division operation

## Description

When Boo encounters a set of two division operations without spaces between them, it treats it as a regex literal.

1/5+3/2 is treated as /5+3/ being a regex literal.

If the division operator were greedier in this instance than turning / / contained literals into regexs, then this problem could be solved. This issue was raised on the mailing list by redacted@googlemail.com. He ran into it when converting Python code into Boo code.

This is a possible fix for this issue. Not really production quality, I don't know enough about the antlr generated parser/lexer to be sure that overriding makeToken won't have some strange issues with regard to lookahead and guessing. But the point of the fix is that we could decide whether / is a division or the start of a regular expression based on the previous significant token. Division is only possible when there is an expression on the left hand side, and an expression should end in one of:

literal number token, identifier, right parentheses, right bracket, increment, decrement.

These cannot legally precede a literal regular expression (as far as I know) so in these cases we can prefer the division operator. (I might be forgetting some tokens that should be added to the list though, I'm not a Boo expert). The "print" macro might precede a regular expression so I made an exception to the "identifier implies division" rule for that. (Macros are a whole other headache anyway).
