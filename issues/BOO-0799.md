### Daniel Grunwald, 13/Feb/07 4:19 PM

We cannot simply Reset the RangeEnumerator because we don't know if the first GetEnumerator() consumer is done.

Someone might do: r = range(3); z = zip(r, r)

Every GetEnumerator call must return a new enumerator. If you want to save allocations by combining the Enumerable with the Enumerator, you can "return this;" for the first GetEnumerator() call only, subsequent calls must create new objects.

This is also how C# 2.0 implements generators:

 public IEnumerable&lt;int&gt; Range(int end)

 {

 for (int i = 0; i &lt; end; i++) 
{
 yield return i;
 }

 }

==&gt;

public IEnumerable&lt;int&gt; Range(int end)
{
 HelperClass d__1 = new HelperClass(-2);
 d__1.initial_end = end;
 return d__1;
}

class HelperClass : IEnumerator&lt;int&gt;, IEnumerable&lt;int&gt;

{

internal int initial_end;

int end; 

int _state; // _state = -2 =&gt; enumerable, _state &gt;= 0 =&gt; enumerator

public HelperClass(int startState) 
{ _state = startState; }

IEnumerator&lt;int&gt; IEnumerable&lt;int&gt;.GetEnumerator()

{

 HelperClass d__1;

 if (Interlocked.CompareExchange(ref this._state, 0, -2) == -2)
 {
 d__1 = this;
 }

 else
 {
 d__1 = new HelperClass(0);
 }

 d__1.end = this.initial_end; // because the MoveNext() might change end, we always need a copy of initial_end for future GetEnumerator calls!

 return d__1;

}

...

}

This is the way you should do it if you want to combine the Enumerable and Enumerator to save an object allocation. Otherwise, just do it like with Boo generators and use two classes.

### Arron Washington, 13/Feb/07 3:49 PM

as far as I know regarding

iter == IEnumerable, not IEnumerator.

iter.GetEnumerator is returning a fresh IEnumerator object, so you can do join(iter) as many times as you want as its just going to return a new IEnumerator object that is ready to be positioned at the first element.

var = iter.GetEnumerator()

join(var)

join(var)

should have the same results as iter = range(3)

Yes, I think the issue is about calling "reset" on IEnumerator objects to bring them to the state they were before they were consumed by the builtin functions.

iter = range(3)

The RangeEnumerator implementation is really an IEnumerable AND an IEnumerator, so when you call GetEnumerator() it just returns a copy of itself, and since you're recylcing the old copy its already moved passed all its elements. Generators don't have this problem because they return a new IEnumerator-based object.

### Cedric Vivier, 13/Feb/07 3:33 PM

I believe both should not reset automatically, they wouln't be a "standard"/verifiable implementation of IEnumerator :

"If MoveNext passes the end of the collection, the enumerator is positioned after the last element in the collection and MoveNext returns false. When the enumerator is at this position, subsequent calls to MoveNext also return false. If the last call to MoveNext returned false, calling Current throws an exception. To set Current to the first element of the collection again, you can call Reset followed by MoveNext."
