## Description

Code generates exception in newest Boo versions but old versions work correct.

def gen():

 yield 'z'

iter = gen().GetEnumerator()

iter.MoveNext()

iter.Reset() //Exception System.NotSupportedException was thrown in debuggee: Specified method is not supported.

I made Reset() throw a NotSupportedException because it might be impossible to re-initialize the locals in the IEnumerator case. Take this method:

```
def ReadFile(a as StreamReader) as IEnumerator[string]:
 try:
 line as string
 while (line = a.ReadLine()) != null:
 yield line
 finally:
 a.Dispose()
```

There's absolutely no way to reset this. I'm OK with an attribute [OldBooEnumerator] / [resetable]. It should call Dispose() and then reset _state and not try to be more intelligent.

Why to call Dispose() from Reset():

Usually finally-blocks in enumerators dispose objects created in the enumerator itself. The resetted enumerator will create a new object, so the old one should be disposed.

E.g.

```
[resetable]
def ReadFile(filename as string) as IEnumerator[string]:
 using sr = StreamReader(filename):
 line as string
 while (line = a.ReadLine()) != null:
 yield line
```

The ReadFile enumerator should close the file handle when Reset() is called and re-open the file on the next MoveNext() call. You get this effect by implementing Reset() as

```
def Reset():
 Dispose()
 _state = 0

```

Note that "yield" inside try-finally is way more frequent than you might think; every "for"-loop uses try-finally to dispose the enumerator!

I think having a [resetable] ast attribute to apply on generator methods is the most sensible option.

When the attribute is applied (hence the developer knows what he's doing and it's his role to make sure the enumerator can indeed reset to its initial state) then boo compiler will instantiate a GenericGeneratorResetEnumerator deriving from our GenericGeneratorEnumerator enumerator, with the Reset() method implemented [1].

[1] and there is two options for the implementation :

the old naive pre-generic behavior that was on boo &lt; 0.8 : reset _state to 0 – the locals being not reinitialized.. but since the developer explicitely says it is a resetable enumerator it's his job to handle this.
 
a more complex approach that would require resetting the locals too [if they are deterministic anyways]
