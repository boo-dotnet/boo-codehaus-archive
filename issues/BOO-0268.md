### Daniel Grunwald, 29/Apr/05 9:02 AM

Fixed.

The problem was that the 'local variable' _b = value in the setter was used to resolve B instead of the field _b. 'value' resolved to the properties type, so we got a stack overflow.

Fields are now tried before the variable is tried to be resolved as local variable.

Moreover, BooBinding now distinguishes between the local variables in the getter and the setter.

### Peter Johanson, 08/Apr/05 12:50 PM

I've managed to find one adverse side effect of this, which is some of the internally used methods, objects, etc that the boo compiler uses during the ProcessMethodBodies step start showing up in the auto completion windows.

For instance, code like:

import System

import Gtk

class MyWindow(Window):

 def constructor(title as string):

 super(title)

 SetDefaultSize(400, 300)

 DeleteEvent += 
{ Application.Quit() }

causes "self." to show "___closure1" since the closure in the construtor internally gets generated as a method for the class during the ProcessMethodBodies step.

If this fix for the Properties thing is used, the addin will probably need to filter anything prefixed with "___" from anything it does (which it makes sense to do since these are things reserved interally for the compiler.

I haven't tried hacking that together yet for my MD addin though.

### Doug H, 08/Apr/05 12:37 AM

Peter Johanson found what appears to be the fix, while working on his MonoDevelop addin which suffered from the same problem. On line 96 in extras/sharpdevelop/boobinding/src/BooParser.cs, change ProcessMethodBodiesWithDuckTyping with StricterErrorChecking.

The error is because the inferred types of properties are not resolved until the ProcessMethodBodiesWithDuckTyping step, which had been removed.
