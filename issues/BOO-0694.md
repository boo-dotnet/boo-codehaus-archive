## Description

When application tries to return exit code to the system, it is not forwarded by booi (zero is always returned instead). The fix is trivial:

— booi.boo.orig Mon Mar 6 13:51:24 2006

+++ booi.boo Thu Mar 9 17:38:11 2006

@@ -119,11 +119,16 @@

 else: 

 try: 

 resolver.AddAssembly(result.GeneratedAssembly)

result.GeneratedAssembly.EntryPoint.Invoke(null, (argv[consumedArgs:],))

+ exitcode = result.GeneratedAssembly.EntryPoint.Invoke(null, (argv[consumedArgs:],))

+ if exitcode is not null:

+ try:

+ Environment.ExitCode = exitcode

+ except e:

+ pass

 except x as TargetInvocationException:

 print(x.InnerException)

 return -1
 
return 0

+ return Environment.ExitCode

 [assembly: SecurityPermission(

 SecurityAction.RequestMinimum,

I'm attaching zip file with diff and testcases (one using Environment.ExitCode and the other using return from Main). Also, as a side note, I'd like to recommend changing error return value from booi from -1 to 255 or 65535 or even Int.MaxValue. Otherwise -1 is not detected as error by if errorlevel in batch files, which compicates checking for errors within them (such as if my application throws, I won't detect an error).

That was done to make code simpler. In .NET there are two ways of returning exit code. 1) by returning it from entry point as a result. 2) by setting Environment.ExitCode. Since there are two ways of doing it, the easiest is to just override Environment.ExitCode if a value is returned from entry point, and always return Environment.ExitCode. Upon booi start it is initialized to zero, thus the default return is zero. That's the same thing runtime seems to be doing, as when in C# I set both Environment.ExitCode and return another value, returned value wins.
