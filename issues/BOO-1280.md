## Description

The CLI actually supports this through op_AdditionAssignment, op_MultiplyAssignment and so on...

I guess Boo should be able to handle these, currently we automatically expand a+=1 into a=a+1 but we could check first that no inplace overloaded operator is applicable.

```
"""
0 : 1
2 : 3
2 : 5
"""
class Foo:
 static _counter = 0

 [getter(Id)]
 _id = 0

 [getter(Value)]
 _value = 0

 def constructor(x as int):
 _id = _counter++
 _value = x

 static def op_Addition(a as Foo, b as Foo):
 return Foo(a._value+b._value)

 static def op_AdditionAssignment(a as Foo, b as Foo):
 a._value += b._value
 return a

a = Foo(1)
b = Foo(2)
print "${a.Id} : ${a.Value}"

a = a + b
print "${a.Id} : ${a.Value}"

a += b
print "${a.Id} : ${a.Value}" #! 2:5 instead of 3:5 (no new Foo object created)

```

### Winner, 29/Mar/10 2:00 PM

I don't think that this is a good idea.

Afaik most .net languages including C# don't support this. C+/CLI supports it despite its dangers because normal C+ allows it.

It works in C++ because you are never allowed to create a copy of a variable without invoking the overloaded assignment operator or the copy constructor. In .net you can't guarantee this, since some other language without support for overloaded assignment such as C# may memcopy a variable at any time.

On value types it is a small performance optimization which is only necessary in high performance numeric code. But at least it is harmless when implemented correctly.

On reference types it subtly changes the semantics of these compound operators:

a=MyInt(1)

b=a

c=MyInt(1)

b+=c

print a,b

Since b+=1 expands to b=b+1 only b changes to 2, and a remains at 1. This changes the reference of b.

If you allowed an inplace modifying += operator both a and b would have the value 2 afterwards since they reference the same instance.

As a library implementor you can never ensure that there are no aliases for the variable on which the user applies the operator. So it can never be used without danger on reference types.

If you really need inplace operations for performance reasons you can offer a normal function which doesn't need to comply with the semantics of +=
