## Description

s[1..2] = t[0..1];// same as s[1] = t[0]

s[0..2] = t[1..3];// same as s[0] = t[1], s[1] = t[2]

p[0..2] = 3;// same as p[0] = 3, p[1] = 3

a = b ~ c; or a = a + b // Create an array from the concatenation of the b and c arrays. However, a "concatenation" operator is better than "+" , which can mean many things.

Dynamic arrays:

arr.Length = 7

This one is a problem because the length property of an array is read only. Yes, it can be emulated by creating a new array with the new length, copying the values, and destroying the old one, but this is bad.

I'm wondering if in IL, dynamic arrays are supported and if the GC knows how to deal with them.

This is what the GC must do:

1) If newLength &lt; oldLength: set newLength and mark the memory as unused at the end of the array

2) if newLength &gt; oldLength:

If the memory at the end of the array is not used and can fit the additional items, claim it and set the new length.
 
Othewise, create a new array, copy the old values, destroy the old array.

Dynamic arrays are useful in collections, such as a queue, where each item takes an ungodly amount of memory.

Memory would be reclaimed with each dequeue operation.

### Daniel Grunwald, 27/Oct/05 3:35 PM

.NET memory allocation doesn't search for free memory, but puts each new object exactly after the previous object. Garbage collection moves the objects to compact them (and to create new space because the allocator cannot use the gaps). This makes allocation much faster than C (where you'd have to use memory from a pool to get good performance), but makes dynamically sized objects impossible.

.NET 2.0 has a method "Array.Resize&lt;T&gt;(ref T[] array, int newSize)" and as you might guess from the "ref" parameters, it creates a new array object.
