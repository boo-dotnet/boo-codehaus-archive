## Description

This has been talked about many different times, but never had a JIRA issue opened about it before.

Now is the time. 

In essence this new feature requires the compiler to directly inject references from Boo.Lang into the assembly being constructed, and ideally would only inject code that is referenced by the assembly being built.

This would allow Boo-based applications to be deployed without the Boo.Lang.dll dependency. 

It is of particular interest to library authors who want to use Boo but don't want to ship Boo.Lang.dll with their assemblies, and, of course, anyone who just does not want or need the entire Boo.Lang assembly.

This is a patch for embedding the Boo.Lang.dll in the assembly emitted by the compiler. It does not selectively pick which IL to include, or even merge the assemblies like ILMerge does. Instead, it embeds Boo.Lang.dll as a manifest resource in the emitted assembly. It then adds two global functions to the assembly, the first one is a module initializer .cctor which is guaranteed to run before any other code in the assembly. All that does is hook up an event listener for the AppDomain.AssemblyResolve event. The other function is the event listener, that listens for this event which is raised when assemblies are not found, and if the assembly in question is Boo.Lang it loads it from the manifest resource and returns it. After loading Boo.Lang it unhooks the event listener to avoid the (admittedly tiny) performance hit of running this function everytime an assembly load fails.

The implications of using the AssemblyResolve event for this are that IF there is a Boo.Lang.dll in the same folder as the assembly, then that will be used. The embedded boo.lang is ONLY used when finding the Boo.Lang assembly has failed by all other means.

To embed there is a compiler option, --embedboo. This can be used for both .exe's and .dll's.

While this solution may seem a bit of a hack, it does solve the underlying problem: people like to be able to distribute a single .exe or .dll. Another benefit of this approach is that the normal code is exactly the same as before, it doesn't depend on its internal version of Boo.Lang which I would imagine makes it play nicer with other assemblies that also use Boo.Lang. And as for the original idea that you could get away with selectively picking which parts of Boo.Lang to include, that's very elegant, but practically speaking I don't think people will worry too much about the 118 Kb of extra space that it takes to use the entire Boo.Lang.dll.

Anyway, use it if you want. This is the first time I've submitted here so I'm not sure how the process works 

And thanks for Boo, it really is an excellent language, I've even started preferring it to Python.
